# Human-Supervised Multi-Agent Research System
## 多代理协同研究与实验系统 — V3.0 完整架构协议

[English](ARCHITECTURE.md)

**文档性质：** 系统架构与运行协议说明书  
**适用范围：** 单一本地研究项目  
**部署环境：** Windows Desktop，本地共享项目目录  
**系统目标：** 通过多个具有不同职责的 AI Agent，自主完成研究设计、工程实现、实验运行、结果审查与多轮迭代，同时确保人类拥有最高控制权。

# 一、系统概述

本系统是一套基于本地共享文件、任务状态机和事件驱动调度（文件监听）构建的多代理研究协作架构。

其基本运行流程为：

**人类定义目标 → 研究规划 → 工程实现 → 实验执行 → 结果审查 → 下一轮研究规划。**

系统能够在一次初始化后持续进行多个研究轮次，无需用户手动在不同 AI 对话之间复制研究任务、实验结果或执行指令。

系统同时满足以下原则：

1. **人类最终控制：** 研究目标、运行时间、资源预算、暂停、终止和重大方向调整由人类决定。
2. **研究与工程分离：** 研究设计和科学判断由研究执行单元负责，代码开发及实验运行由工程执行单元负责。
3. **自主任务分解：** 主执行单元可以根据任务复杂度动态创建和管理临时 Subagents。
4. **轻量调度：** 没有新任务时，仅执行最低限度的状态检查，避免无意义的完整上下文读取。
5. **文件驱动通信：** 各执行单元通过规范化文件交换指令、结果和持久状态，不依赖彼此的聊天历史。
6. **可审计与可复现：** 研究任务、实验产物、模型指标和代码版本均应可追溯。
7. **显式生命周期：** 系统初始化后默认不运行。只有收到人类的开始命令才允许启动自动调度，收到结束命令后必须停用调度。
8. **保护现有资产：** 不因部署协作系统而重建项目、覆盖训练数据、删除历史实验或破坏已有模型。

本协议定义的是目标架构。具体功能是否已成功部署，必须通过实际的文件、调度器状态和端到端测试验证，不能仅凭 Agent 的文字声明认定成功。

# 二、系统角色与职责

系统采用三层逻辑结构。

## 2.1 Human Control Layer

人类是项目最终负责人，拥有最高决策权限。

人类可以通过专门的交互对话，用自然语言提出研究意见、修改实验约束、要求阶段性汇报、调整自主研究轮次及发出启动、暂停、继续或终止命令。

交互层负责将明确的操作意图转化为结构化控制文件，并向人类报告指令是否已登记、是否被研究系统接收、是否已经实际执行。

普通的研究讨论不应自动被视为执行授权。

交互对话无需定时启动，仅在人类主动使用时运行。

## 2.2 Research Layer

研究层承担科学研究的决策职责，包括：

- 读取研究背景、历史实验和已有证据。
- 提出、比较和修正研究假设。
- 设计具备可验证或可证伪条件的实验。
- 定义数据范围、统计方法、评价指标和验收标准。
- 审查工程层返回的实验结果。
- 区分实验成功、模型性能改善和研究假设获得支持这三种不同结论。
- 判断应继续实验、修正方法、改变方向或结束研究。
- 维护研究进展、证据记录与最终报告。

研究层不能以增加实验数量代替科研进展，也不能为了得到预期结果而任意修改研究定义、样本范围或评估方式。

## 2.3 Engineering Layer

工程层承担技术实现和实验执行职责，包括：

- 阅读正式研究任务。
- 检查和复用现有代码。
- 编写、修改与测试程序。
- 执行模型训练、评估和数据分析。
- 管理实验参数、运行环境和产物。
- 检查实现错误、数据泄露、性能问题与工程可复现性。
- 管理本地 Git 版本记录。
- 生成正式实验结果报告，并将结果交回研究层。

工程层可以自主解决一般实现问题，但不能未经授权改变核心研究目标、实验定义或评价标准。

科研决策、工程执行和人工控制各自拥有明确的职责边界。

# 三、现有项目的保护原则

系统部署在一个已经存在的本地项目中，而非从零开始的新仓库。

该项目包含研究交接文档 `HANDOFF.md`、任务说明、提交规范、Python 源代码、Jupyter Notebook、训练及验证数据、模型权重和历史实验目录。

初始化过程必须首先检查实际目录，理解已有工作状态，不得根据文件名推测研究内容。

现有 `HANDOFF.md` 作为长期研究记录保留。它可以持续维护和追加内容，但不作为直接执行任务的触发器。

正式工程任务必须通过独立的结构化任务信号发布，避免研究记录的普通修改被误判为新任务。

新系统仅增加独立的 `.bridge/` 通信目录，不强制改变原有代码和数据目录。

# 四、共享文件通信架构

所有参与单元必须能够访问同一个真实的 Windows 本地项目目录。正常协作不依赖隔离的 Git Worktree、远程副本或临时工作目录。

标准通信目录如下：

```text
PROJECT_ROOT/
├── HANDOFF.md
├── [existing project files]
│
└── .bridge/
    ├── PROTOCOL.md
    ├── PROJECT_CONSTRAINTS.md
    ├── CLAUDE_STATE.json
    ├── CODEX_STATE.json
    ├── PROJECT_STATUS.md
    ├── FINAL_REPORT.md
    │
    ├── signals/
    │   ├── claude_task.json
    │   └── codex_result.json
    │
    ├── tasks/
    ├── results/
    ├── locks/
    │
    ├── operator/
    │   ├── CONTROL.json
    │   ├── OPERATOR_STATE.json
    │   ├── requests/
    │   └── acknowledgements/
    │
    └── watcher/
        ├── bridge_watcher.ps1      # 事件驱动 Dispatcher
        ├── bridgectl.ps1           # 人类控制命令
        ├── live_view.py/.html      # 只读实时视图（浏览器查看两个 agent 的输出，由 watcher 保持运行）
        ├── *_WORKER_PROMPT.txt     # 两个 Worker 的启动 prompt
        └── OPERATOR_PROMPT.md      # Operator 对话的角色说明
```

文件名称保留既有协议中的约定，以兼容此前的部署；系统的行为规则不依赖某个具体模型品牌。

各文件职责如下。

| 文件或目录 | 用途 |
|---|---|
| `PROTOCOL.md` | 统一通信规范、状态定义、文件权限及故障恢复规则 |
| `PROJECT_CONSTRAINTS.md` | 本项目的目标、评价方式、受保护文件、数据规则、截止时间与算力约束（部署时填写） |
| `CLAUDE_STATE.json` | 研究层当前状态、已处理结果、研究轮次及决策进展 |
| `CODEX_STATE.json` | 工程层当前状态、正在执行的任务和执行结果 |
| `PROJECT_STATUS.md` | 供人类阅读的项目进度与阶段性研究摘要 |
| `signals/claude_task.json` | 最新正式研究任务的发布信号 |
| `signals/codex_result.json` | 最新正式实验结果的发布信号 |
| `tasks/` | 每轮研究任务的完整、不可变快照 |
| `results/` | 每轮实验的完整、不可变报告 |
| `locks/` | 并发互斥及任务重复执行保护 |
| `operator/CONTROL.json` | 人类生命周期与资源控制 |
| `operator/requests/` | 人类新增研究意见及操作请求 |
| `operator/acknowledgements/` | 研究系统对人类请求的处理回执 |
| `FINAL_REPORT.md` | 阶段结束或项目完成后的综合报告 |
| `watcher/` | 事件驱动 Dispatcher、人类控制命令、Worker 与 Operator prompt、运行日志 |

## 4.1 文件所有权

系统采取**单一写入者原则**。

每类共享文件都应有唯一的权威写入方。其他参与者可以读取，但不得同时修改。

研究层独占发布研究任务、研究状态及科研报告。

工程层独占发布实验结果、工程状态及正式工程版本。

人工交互层独占修改用户控制文件及用户请求记录。

研究层和工程层均不得擅自修改人类控制状态。

所有正式 JSON 信号和结果文件应先写入临时文件、完成校验，再通过同一文件系统内的原子替换发布，防止另一参与者读取到不完整文件。

# 五、任务与结果交付协议

## 5.1 任务编号

所有正式研究任务采用唯一递增编号：

`R0001 → R0002 → R0003 → ...`

`R0000` 保留用于首次通信测试，不计入正式研究轮次。

每个任务对应唯一的任务快照和结果报告：

```text
.bridge/tasks/R0001.md
.bridge/results/R0001.md
```

已正式发布的任务快照和终态报告原则上不可覆盖。

## 5.2 研究任务发布

每轮任务至少包含以下信息：

- Research Objective：研究目标
- Existing Evidence：现有证据
- Hypothesis：待检验假设
- Required Implementation：工程需求
- Data & Methodology：数据、方法及统计约束
- Expected Outputs：预期代码与实验产物
- Acceptance Criteria：验收标准
- Constraints：数据、计算资源及执行限制
- Next Decision：不同结果对应的下一步研究决策

任务应具有明确边界，不允许把大量无关问题堆叠成单个无法验收的任务。

研究层首先创建完整的任务快照，在确认内容有效后，再原子更新最新任务信号。

## 5.3 工程执行与回传

工程层在接收到有效的新任务后，领取任务执行权并完成实现和实验。

任务结束后形成正式报告，包含：

- 任务编号与执行状态
- 实际代码变更
- 数据和运行环境
- 实验参数及随机种子
- 运行命令和重要日志
- 实际评价指标及统计结果
- 生成的图表、数据、权重与文件路径
- 测试与验收情况
- Git Commit SHA 与代码状态
- 失败原因和未解决问题
- 对下一轮研究的建议

终态结果分为：

**SUCCESS：** 工程执行完成，实际验收情况如实记录。

**FAILED：** 执行失败或任务未能完整完成。

**BLOCKED：** 缺少数据、权限、环境、依赖或必要研究定义，无法安全继续。

SUCCESS 不等于研究假设成立。

工程结果发布顺序必须是：先完成报告，再发布结果信号，最后更新工程状态。

## 5.4 研究反馈与下一轮任务

研究层收到新的终态结果后，核验任务编号、实验方法、实际产物和结果可靠性，再决定是否进行下一轮。

不能仅根据工程层的文字总结接受重要科学结论。

未经处理的实验结果必须先完成研究审查；前一轮任务仍在进行时，不得覆盖其任务指针。

信号文件用于快速通知，完整任务和结果快照才是权威记录。若发生信号丢失或状态不一致，系统应根据持久化快照进行恢复。

# 六、事件驱动 Dispatcher（V3.0 实现）

> 早期版本使用两个定时调度任务（研究侧每 5 分钟、工程侧每 3 分钟）。那种方式即使没有工作也要定期调用模型，交接最多要等一个周期。V3.0 改为一个本地文件监听进程，交接延迟降到秒级，空闲时不消耗 token。

系统只设置一个由人类启动的本地进程：`.bridge/watcher/bridge_watcher.ps1`（Windows PowerShell `FileSystemWatcher`）。每个项目只允许一个实例。

Dispatcher 与 Worker 仍是逻辑阶段，不要求创建永久 AI Chat。

## 6.1 Phase A：Lightweight Dispatch（不调用模型）

`.bridge/` 中的信号、控制、锁或状态文件一发生变化（去抖约 1.5 秒），或者某个 Worker 进程退出时，watcher 立即运行两个标准库 Python 探针：

- `dispatcher.py probe`：工程侧是否有可领取的正式任务；
- `claude_bridge.py probe`：研究侧是否有新结果、新用户意见、R0000 启动或恢复工作。

探针只读取最小必要的控制、任务和状态文件，检查内容与原设计相同：生命周期是否允许运行、是否有新任务、是否有未处理结果、是否有新意见、任务是否已完成、是否有并发冲突。

没有新工作时不启动任何 Agent，也不消耗 token。仅在 STARTING / ACTIVE 期间，watcher 每 60 秒额外用 Python 复查一次，用来兜住遗漏的文件事件；这一步同样不调用模型。

空闲检查不得加载数据集、模型权重、Notebook 或历史记录，不得创建 Subagents、训练模型或提交 Git。

## 6.2 Phase B：Research / Engineering Worker

只有探针确认存在有效工作时，watcher 才以无人值守方式启动对应的 Worker 进程：

- 工程侧 `CANDIDATE` → `codex exec`（prompt：`watcher/CODEX_WORKER_PROMPT.txt`）；
- 研究侧 `WORK` → `claude -p`（prompt：`watcher/CLAUDE_WORKER_PROMPT.txt`）。

每个角色同时最多一个进程。Worker 在本次执行内完成工作，把持久状态写回共享目录后退出。一方发布任务或结果后，另一方在数秒内被启动。

Worker 运行在独立的隐藏控制台中：关闭 watcher 窗口不会打断正在执行的任务，重新打开 watcher 会接管仍在运行的进程，而不是重复启动。

## 6.3 防重复与防空转

- Worker 正常退出但工作状态没有变化（说明它没有完成）时，不再重复启动，标记为 stalled 并提醒人类。
- Worker 异常退出（崩溃、额度耗尽、网络问题）时，延迟 120 秒重试一次；再失败即停止重试（对应 10.4 节）。
- 锁、已完成任务账本和不可变快照仍是防止重复执行的权威机制。

## 6.4 生命周期记账

watcher 只做确定性的机械记账，从不调用模型：

- 记录运行周期的开始与关闭（`record-watcher`，幂等）；
- 每个 STARTING 周期执行一次通信检查（`connectivity-check`）；
- 新周期开始时，把上个周期未完成的任务重新指向新的 `run_id`。

IDLE、STOPPING、STOPPED 状态下不启动任何 Worker，也没有周期性检查。

# 七、Dynamic Subagent Orchestration

研究及工程主执行单元均可以在正式任务内，根据任务复杂度自主创建、管理和结束临时 Subagents。

子代理数量并非固定编制。

默认每个主执行单元最多同时运行 **3 个 Subagents**，不包括主 Agent。

## 7.1 创建条件

只有进入正式 Worker 阶段，且当前生命周期允许执行任务时，才可以创建执行型 Subagents。

简单任务优先由主 Agent 独立完成。

复杂任务可以拆解为多个相互独立的子任务，以提高并行效率、减少主上下文污染并强化独立审查。

不得仅为展示多代理能力而创建不必要的子代理。

## 7.2 动态职责

研究类 Subagents 可以承担：

- 假设分析
- 统计方法审查
- 文献与研究记录调查
- 实验方案设计
- 泛化与过拟合分析
- 独立研究批判

工程类 Subagents 可以承担：

- 代码库分析
- 模块实现
- 测试与验证
- 性能优化
- 实验日志分析
- 独立代码审查

这些只是可选职责，实际分配取决于当轮任务。

## 7.3 子代理权限

每个子代理必须获得明确的 Parent Task ID、子任务目标、允许访问的文件范围、预期结果、验收条件及停止条件。

子代理不得绕过主 Agent 直接发布正式跨系统结果，不得修改人工控制文件，也不得自行提交 Git 或改写共享协议。

原则上不允许递归创建下一级 Subagents，除非人类另行授权。

多个子代理同时修改代码时，必须划分文件所有权，避免并发写入同一 Notebook、代码文件或模型产物。

## 7.4 资源与成本限制

并行执行必须考虑真实的 CPU、GPU、内存和文件系统资源。

默认不允许多个大型模型训练任务无约束地争用同一 GPU。

Subagents 的使用应当带来实际的并行收益、上下文隔离或质量提升。增加子代理数量并不意味着总 token 成本一定降低。

所有子任务最终由主 Agent 统一验收和整合。

# 八、Human Control Layer

人类通过专门的 Operator 对话与研究系统交互，而不需要直接编辑 JSON 文件。

Operator 可以解释研究进度、登记新意见、调整研究预算、更新控制状态和查询实验结果。

该交互入口由人类主动使用，不承担长期轮询。

## 8.1 生命周期状态

系统定义以下生命周期：

| 状态 | 含义 |
|---|---|
| IDLE | 初始化完成，尚未收到开始命令 |
| STARTING | 正在检查条件并启动调度 |
| ACTIVE | 自动研究与实验允许运行 |
| STOPPING | 已禁止新任务，正在停止执行和调度 |
| STOPPED | 本轮研究已结束，watcher 不再派发 |

此外，控制模式支持：

- RUN：允许正常研究。
- PAUSE_AFTER_ROUND：当前指定任务结束后暂停。
- PAUSE_NOW：在安全检查点尽快暂停。
- STOP：禁止继续自动研究。

生命周期和控制模式共同决定是否允许启动新的任务。

## 8.2 开始命令

**系统只有在收到人类明确发出的“开始研究”命令后，才能激活自动监测与研究执行。**

初始化项目、创建 Git 仓库、创建通信目录、配置 Subagents、部署和打开 watcher，都不构成启动授权。

开始流程：

1. Operator 验证用户授权。
2. 确认 watcher 正在运行，且上一个运行周期已经关闭（否则拒绝开始）。
3. 创建唯一的运行周期标识 `run_id`，将生命周期设为 STARTING。
4. watcher 记录新周期并执行通信检查，验证双方能够访问同一个项目目录。
5. 将状态转为 ACTIVE。
6. 首次运行先开展 R0000 通信测试。
7. 通信测试通过后再进入正式研究。

以上步骤由 `bridgectl start` 一次完成。watcher 没有运行时，只修改控制文件不会启动任何工作，因此 `start` 会直接拒绝。

## 8.3 结束命令

**人类发出“结束研究”后，不仅要停止发布新任务，还必须停用周期性调度。**

结束流程：

1. 将生命周期置为 STOPPING。
2. 禁止领取和发布新的正式任务。
3. 停止创建新的 Subagents。
4. 请求已运行任务在安全检查点结束或中断。
5. 保存必要的部分实验结果与恢复状态。
6. watcher 立即停止派发，并记录该运行周期已关闭。
7. 核实没有 Worker 进程、工程锁或研究锁仍在运行。
8. 将生命周期更新为 STOPPED（`bridgectl end`；仍有工作在收尾时报告 PARTIALLY_STOPPED，稍后再执行一次）。

如果不能确认两端都停止，应报告部分停止状态，不得虚报系统已完全终止。

特别注意：停止派发、停止正在运行的 Agent 进程、终止已启动的训练进程，是三种不同操作。

紧急停止由人类结束 `bridgectl status` 显示的进程，必要时还须处理独立的训练进程。

## 8.4 停止后的要求

STOPPED 状态下：

- 不得继续自动轮询。
- 不得发布新研究任务。
- 不得执行模型训练。
- 不得自动生成新实验。
- 不得创建执行型 Subagents。
- 不得自动进行 Git Commit。
- 不得因旧 READY 信号而自行恢复运行。

原有代码、模型、实验数据、任务记录、Git 历史和研究结论均保留。

重新启动必须再次获得人类明确授权。

## 8.5 人类研究意见

普通研究意见通过独立 Request 文件记录，例如：

`.bridge/operator/requests/U0001.md`

每条请求具有唯一编号、请求类型、适用轮次和处理状态。

系统应区分：

- 已登记
- 已接收
- 已执行
- 已延期
- 需要用户进一步决定
- 未采纳并说明原因

新研究意见默认在下一轮研究规划时考虑，除非用户明确要求立即改变当前任务。

用户指令不得被静默丢弃。

# 九、Git 版本管理协议

项目使用单一本地 Git 仓库，原则上维持简单、可追溯的线性版本历史。

## 9.1 初始化

首次部署时检查项目是否已经存在 Git 仓库。

如果不存在，则初始化本地仓库，建立适合 Python、Jupyter 和模型训练项目的 `.gitignore`。

创建经过审查的 Initial Baseline Commit，保存引入多代理系统前的代码状态。

默认不创建远程仓库，不自动 Push，也不将项目公开。

## 9.2 文件排除

默认排除：

- Python 缓存
- Notebook 临时检查点
- 虚拟环境
- 密钥与敏感配置
- 大型原始训练和验证数据
- 大型模型权重
- 可重新生成的大型实验中间产物
- `.bridge/` 中的动态运行状态、信号和锁文件

需要追踪的代码、配置、任务规范和可复现实验脚本应按实际用途审查。

被 `.gitignore` 排除的文件并不会获得 Git 版本保护，因此大型原始数据、模型权重和通信历史应有独立的备份方案。

## 9.3 每轮实验 Commit

正式研究轮次中，工程层完成经过验证的代码修改后，应为对应 Task ID 创建 Git Commit。

每轮实验报告应记录：

- Base Commit SHA
- Result Commit SHA
- 修改文件
- 实验实际使用的代码状态
- 未提交的代码变更
- 必要的复现说明

如果仅运行实验而没有修改代码，可以直接记录现有 Commit SHA，不必创建空提交。

如果实验运行于尚未提交的工作区状态，必须如实记录，不得声称已有 Commit 完整代表实验代码。

## 9.4 Git 安全规则

禁止无条件暂存所有文件，避免将其他 Agent 的研究记录或人工控制文件意外加入工程提交。

不得擅自执行破坏性 Reset、Clean、强制 Checkout、历史重写或远程 Push。

模型表现下降也不意味着应自动回滚代码。

回滚应当作为新的、可审计的工程决策执行。

Git 用于追踪代码和实验版本，不承担 Agent 消息队列的职责。

# 十、并发、幂等性与故障恢复

## 10.1 防重复执行

每个正式任务只能由一个有效工程执行者领取。

研究审查同样不能由多个实例同时发布下一轮任务。

系统使用文件系统支持的原子独占操作创建互斥锁。

不能仅依靠文件修改时间判断是否应该重新执行任务。

## 10.2 任务幂等性

对于同一个 Task ID：

- 已完成的任务不得重复训练。
- 已正式发布的结果不得重复覆盖。
- 已处理的实验结果不得重复分析并派发下一轮。
- 发生部分写入故障时，应先检查并恢复当前事务。
- 无法判断是否已经执行时，应暂停并报告，而非盲目重试。

## 10.3 遗留锁

如果发现锁文件存在，但对应任务状态不明确，系统应检查实际运行情况。

不能仅因为锁文件创建时间较久就认定可以安全删除。

无法确认锁所有者是否仍在运行时，应进入阻塞状态并请求处理。

## 10.4 失败恢复

任务失败后，需要区分：

- 研究假设被否定
- 代码执行错误
- 运行环境异常
- 数据质量问题
- 计算资源不足
- 实验定义不完整
- 自动交接失败

不同类型的失败需要不同处理策略。

不能把所有失败都简单转换为“重新运行一次”。

连续遇到相同不可恢复错误时，应停止自动重试，保留证据并请求人工介入。

# 十一、Token、上下文与计算预算

系统的主要效率策略不是不断增加 Agent，而是降低无意义工作。

具体原则：

1. 主研究对话不承担高频文件检查。
2. watcher 先用 Python 检查轻量状态文件，不调用模型。
3. 没有新工作时立即退出。
4. 有工作时才读取完整研究资料。
5. 子代理只接收必要的局部上下文。
6. 大型日志和产物保留在磁盘，不全部写入主上下文。
7. 不重复读取与当前任务无关的历史。
8. 不为简单任务创建不必要的 Subagents。
9. 不无约束地并行训练大型模型。
10. 不因追求更高指标而进行没有统计控制的无限参数搜索。

默认正式研究预算为 **8 轮**，R0000 不计入。

每轮结束后必须判断是否有继续研究的价值。

达到预算上限后，停止发布新任务，形成阶段总结并等待人类决定是否继续。

# 十二、项目状态与研究审计

研究层维护 `PROJECT_STATUS.md`，供人类交互层读取和解释。

该文件至少应记录：

- 当前研究目标
- 当前运行周期
- 当前任务编号
- 已完成研究轮次
- 研究层状态
- 工程层状态
- 最近完成的实验
- 主要评价指标
- 已获得的研究结论
- 已否定或仍待检验的假设
- 最新人类意见及处理状态
- 下一步计划
- 当前风险或阻塞
- 最近一次有效状态更新时间

研究层每次作出新的研究方向决策，都应留下简短 Decision Record。

记录应说明：

1. 本轮实验提供了什么证据。
2. 哪些结论可以接受。
3. 哪些问题依然不确定。
4. 为什么选择下一项实验。
5. 为什么没有选择其他方案。
6. 下一项实验预计消除什么不确定性。

这样能够防止多代理系统在长时间运行后失去研究逻辑的连续性。

项目完成或阶段结束时，应形成完整 `FINAL_REPORT.md`，关联全部重要任务、实验产物、模型变化、Git 版本和研究结论。

# 十三、首次部署与验收流程

首次部署分为五个阶段。

## Stage 1：项目检查与保护

确认项目真实目录、已有数据、现有模型、历史实验和研究文档。

不启动正式训练。

## Stage 2：Git 与通信层初始化

初始化或沿用本地 Git 仓库，建立安全的忽略规则和 Baseline Commit。

创建 `.bridge/` 目录、协议文件及状态文件，检查文件所有权和访问权限。

## Stage 3：Agent 与 Dispatcher 配置

准备研究端、工程端、人工交互入口和动态 Subagent 配置。

配置 watcher、Worker prompt 和 `PROJECT_CONSTRAINTS.md`（由 research-bridge-kit 的 `deploy.py` 一次生成）。生命周期保持 IDLE。

系统此时应报告 READY_TO_START，而不是 ACTIVE。

## Stage 4：人类授权与 R0000 测试

只有收到“开始研究”命令，才通过 `bridgectl start` 进入 ACTIVE。

启动后先执行 R0000 只读通信测试，验证：

- 双方使用同一个项目目录。
- 研究任务能被正确发布。
- 工程任务能被自动领取。
- 工程结果能被写回。
- 研究端能自动识别结果。
- 重复检查不会造成重复执行。
- 人类控制状态能够被双方正确读取。

测试不应修改现有模型、原始数据和正式工程代码。

## Stage 5：正式研究运行

R0000 通过后，根据已有研究证据发布 R0001。

此后按以下流程迭代：

**研究规划 → 正式任务 → 工程实现 → 实验执行 → 结果回传 → 研究审查 → 下一轮任务。**

每轮均需有对应任务 ID、实验报告、研究决策和可复现记录。

持续运行直到目标完成、预算达到上限、出现不可恢复阻塞，或者人类要求暂停或结束。

# 十四、安全边界与实施限制

本系统默认禁止未经授权的以下行为：

- 删除或覆盖原始训练数据。
- 擅自覆盖已有模型权重。
- 将私有研究资料上传到外部服务。
- 自动提交正式课程作业。
- 自动创建公开代码仓库或推送代码。
- 擅自执行实盘交易或外部资金操作。
- 绕过人类控制状态启动隐藏任务。
- 在 STOPPED 后继续进行周期性轮询。
- 假装创建了实际不存在的 Scheduled Task、Chat 或 Subagent。
- 假装文件控制能够瞬间杀死正在运行的系统进程。
- 在缺少实际产物时编造模型性能、科研结论或测试结果。

共享控制文件能够传递生命周期指令，但不能瞬间中断一个已经在运行的进程；Worker 只能在安全检查点响应停止。

若无法自动完成启动、暂停或终止，应明确报告，并要求人类完成必要的手动操作。

同样，人工交互入口可以是任何能在项目目录执行命令的 Claude 对话（桌面版 Code 页签或命令行），后台研究由 watcher 启动的 Worker 执行，不应因此阻断整个系统。

系统不得为了声称“完全自动化”而掩盖真实的技术限制。

# 十五、最终运行原则

本系统采用以下权力与职责结构：

**人类负责目标、边界、授权和最终决策。**

**研究层负责科学判断、假设设计、结果审查和研究方向。**

**工程层负责代码实现、实验执行、质量验证和版本追踪。**

**Dispatcher 负责在授权运行期间发现新工作，并按需进入 Worker 阶段。**

**Subagents 负责在主 Agent 管理下完成具有明确边界的临时专业任务。**

**共享通信层负责持久状态、任务交接、结果归档、重复执行保护和故障恢复。**

整个系统的核心并非让多个 AI 无限互相对话，而是建立一条**可控制、可审计、可恢复、可复现、计算成本可管理的自动研究流水线**。

它应在没有新工作时保持轻量，在需要时自主组织复杂研究与工程任务，在收到人类干预时调整方向，并在明确结束后真正停止周期性工作。

最终目标是让人类从机械的任务转发者转变为研究项目的监督者与决策者，同时确保 AI 的自主执行始终处于明确的授权范围之内。
